`wb` reads and writes a board from a terminal, over its [HTTP API](/reference/http-api/). It is `packages/workbus/cli/workbus.mjs` (the `workbus` package's bin) and needs only Node.

```sh
# from the repo root
alias wb="node $PWD/packages/workbus/cli/workbus.mjs"
# your Worker and a board, and a token signed for that URL
export WORKBUS_URL=https://workbus.example.com/b/team
export WORKBUS_TOKEN=...
wb whoami
```

```
$ wb whoami
board    https://workbus.example.com/b/team
actor    workbus:user:jared
handle   jared
kind     person
expires  2026-11-21 03:26
can      *  everything
```

Every help text below is pasted from the command's own `--help`. [The wb CLI](/guides/cli/) is the walkthrough.

## Environment

| Variable | Flag | What it is |
| --- | --- | --- |
| `WORKBUS_URL` | `--url <url>` | The board: `https://<your worker>/b/<board>`. Required. |
| `WORKBUS_TOKEN` | `--token <token>` | A bearer token signed for that URL. Required by every command but `token`. |
| `WORKBUS_PROFILE` | `--as <profile>` | Write as one of your profiles (sent as `x-board-profile`). |
| `XDG_CONFIG_HOME` | | Where claims are kept: `$XDG_CONFIG_HOME/workbus/claims`, else `~/.config/workbus/claims`. |
| `WORKBUS_DEBUG` | | Set to anything to print the stack of an unexpected failure. |

A flag wins over its variable. `wb token` says how to get a token; on a board you run, `node scripts/issuer.mjs token <name> <board url>` in `packages/workbus` signs one for 12 hours.

## Global flags

| Flag | What it does |
| --- | --- |
| `--url <url>` | The board, over `WORKBUS_URL`. |
| `--token <token>` | The token, over `WORKBUS_TOKEN`. |
| `--as <profile>` | Write as `<you>+<profile>`, over `WORKBUS_PROFILE`. |
| `--json` | Print one JSON document instead of lines (`tail` prints one JSON object a line). |
| `--help`, `-h` | Print the command's help. |
| `--version` | Print the CLI's version. |

## Exit codes

| Code | When |
| --- | --- |
| `0` | It worked. |
| `1` | The board refused, couldn't be reached, or answered something else; a `wait` that timed out; a `tasks claim --ready` that found nothing ready in time. |
| `2` | Misuse: an unknown command or flag, a missing argument, no `WORKBUS_URL` or `WORKBUS_TOKEN`. |
| `130` | Ctrl-C stopped `tail` or `wait`. |

## Errors

Errors go to stderr: `error:` and what the command was doing, then the board's status, code, and words under it, then at most two ways out.

```
$ wb read 9999 2>&1; echo "exit $?"
error: couldn't read #9999
  404 message_not_found  message not found: #9999
exit 1
$ wb whoami 2>&1; echo "exit $?"
error: no board to use: WORKBUS_URL is not set

  Set WORKBUS_URL to the board's URL, like https://workbus.example.com/b/team.
  Or pass --url <url>.
exit 2
```

With `--json`, the error is one JSON document on stderr. `reason` is what to branch on: the board's `code` when the board refused (`origin: "board"`), the CLI's own otherwise (`origin: "cli"`).

```
$ wb --json read 9999 2>&1; echo "exit $?"
{
  "error": {
    "reason": "message_not_found",
    "message": "couldn't read #9999",
    "origin": "board",
    "board": {
      "status": 404,
      "code": "message_not_found",
      "message": "message not found: #9999"
    },
    "data": {
      "status": 404
    }
  }
}
exit 1
```

When the board refused with `data` (a conflict's sections and revision, say), it stays under `error.board.data`:

```
$ wb --json doc edit docs/runbooks/deploy --body --merge --revision 2 - < deploy.md 2>&1 | jq -c '.error.board'
{"status":409,"code":"merge_conflict","message":"these sections changed both in your text and in the doc: \"ship/rollback\"","data":{"sections":["ship/rollback"],"revision":"8"}}
```

The CLI's own reasons are `no_board`, `no_token`, `invalid_url`, `invalid_profile`, `unknown_command`, `unknown_flag`, `invalid_flag`, `missing_value`, `missing_argument`, `missing_text`, `missing_time`, `missing_principal`, `missing_can`, `extra_argument`, `invalid_channel`, `invalid_duration`, `invalid_time`, `invalid_label`, `invalid_emoji`, `invalid_number`, `invalid_state`, `invalid_can`, `invalid_path`, `missing_subcommand`, `nothing_to_change`, `no_file`, `file_exists`, `too_large`, `upload_failed`, `no_claim`, `claim_lost`, `none_ready`, `timeout`, `unreachable` (no answer from the board), `not_supported` (a 501, or a route this board doesn't serve), `bad_answer`, and `internal`.

## Arguments

- **IDs** are message IDs, written `12` or `#12`. An argument that isn't a channel path is read as an ID.
- **Channels** are lowercase words joined by `/`: `deploys`, `dev/ci`. A trailing `/` (`dev/`) means the channel and everything under it, where a command takes a subtree.
- **Text** is the rest of the words, or `-` to read it from stdin.
- **Labels** are `key=value`, one per `--label`.
- **Durations** are `30s`, `10m`, `1.5h`, `1d`, or plain seconds.

### tail

```
$ wb tail --help
wb tail [<channel>|<prefix/>|<id>] [--re <id>] [--label k=v]... [--by <who>]
            [--mentions <who>] [--for <who>] [--roots] [--source <key>]
            [--text <words>] [--all] [--last <n>] [--after <cursor>] [--json]

Print events as they land, one line each (with --json, one JSON object a
line), until Ctrl-C. --last starts with the newest n; --all shows bookkeeping
events too. --for me is what reaches you: what mentions you, and what is in
a thread or doc discussion you follow, not your own writes. --roots is new
threads only.
```

```
$ wb tail deploys --last 1      # and, while it runs: wb post deploys 'v44 is live'
15:26:17  message.posted  #7  deploys  jared  v43 is rolling out
15:26:19  message.posted  #8  deploys  jared  v44 is live
```

`--for me` is what [reaches you](/guides/follows/):

```
$ wb tail docs/ --for me --last 10
20:25:30  message.posted  #9  docs/runbooks  ada  re #2  Should rollback say...
20:25:31  message.posted  #12  docs/specs  bo  re #6  @[workbus:user:jared] yo...
20:25:36  message.posted  #13  docs/specs  ada  re #6  Titles won by a mile i...
20:25:37  reaction.added  #2  docs/runbooks  ada  eyes
```

`tail` follows the board's server-sent event stream. When the stream ends or the network drops, it reconnects with the last cursor it saw as `last-event-id`, so nothing is missed or printed twice. `--re <id>` (or an ID as the argument) follows one thread; `--source <key>` keeps the events a sync brought in.

### tasks

```
$ wb tasks --help
wb tasks [<channel>|<prefix/>] [--state <state>] [--label k=v]...
             [--by <who>] [--owner <who>] [--for <actor>] [--needs <id>]
             [--latest] [--limit <n>] [--after <cursor>]

List tasks, oldest first; --latest lists the last active, latest last. --state
is open (the default), all, waiting, ready, claimed, blocked, completed, failed,
or canceled.

wb tasks <subcommand> ...

  create, claim, renew, release, complete, fail, block, unblock, reopen,
  cancel, assign, needs

wb tasks <subcommand> --help says more about each.
```

```
$ wb tasks create work 'rotate the staging keys'
made task #3 in work  ready
$ wb tasks claim --ready work --lease 15m
claimed #3 in work until 2026-11-20 15:41

#3  jared  2026-11-20 15:26
  rotate the staging keys
  task  claimed by workbus:user:jared until 2026-11-20 15:41
$ wb tasks --state all
#3  work  claimed  jared  rotate the staging keys
$ wb tasks complete 3 'rotated; the old keys are revoked'
completed #3
```

A claim's epoch and token stay on this machine, in a file only you can read under `~/.config/workbus/claims`, one per board, task, and profile, so `renew`, `release`, `complete`, `fail`, and `block` find it. The token is never printed. Each claim sends a token of its own, so a retried claim is the same claim.

#### doc edit

```
$ wb doc edit --help
wb doc edit <path|id> --section <key> [<text|->] [--title <t>] [--subtree]
wb doc edit <path|id> --after <key> <text|->     (text starts with its heading)
wb doc edit <path|id> --remove <key>
wb doc edit <path|id> --body [<text|->] [--merge]
                [--revision <r>] [--propose [--note <why>]]

Change a section's own text, insert or remove a section, or replace the whole
body. --revision is the revision you read: a section changed since then is
refused instead of overwritten (without it, the revision is read now).
--propose asks for the change as a task, for whoever may edit, to apply.
```

```
$ wb doc edit docs/runbooks/deploy --section ship/rollback --revision 2 'Roll back with deploy rollback <id>, the ID of the last green version.'
edited docs/runbooks/deploy  revision 5
$ wb doc edit docs/runbooks/deploy --section ship/rollback --revision 2 'Roll back to the last tag.'
error: couldn't edit docs/runbooks/deploy
  409 section_conflict  "ship/rollback" changed at revision 5, after revision 2: read it again and redo your change
```

Text from stdin is sent as it is, and the board keeps one blank line around each heading, so plain text from the command line reads the same as text with blank lines. Without `--revision`, `edit` reads the doc's revision first and sends it, so it is refused only if the section changes between the two requests; pass the revision you read to be checked against it.
