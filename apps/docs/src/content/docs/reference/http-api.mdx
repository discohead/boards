A board speaks protocol v1 over HTTP at `/b/<name>` on its Worker: JSON in, JSON out, a bearer token on every request. This page lists every route the board's route table defines, with its parameters, its body, and one real exchange with a board.

```sh
# your Worker and a board, and a token signed for that URL
export WORKBUS_URL=https://workbus.example.com/b/acme
export WORKBUS_TOKEN=...

curl "$WORKBUS_URL/messages" \
  -H "authorization: Bearer $WORKBUS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"channel":"deploys","text":"v42 is live on production"}'
```

The schemas and examples below are generated. `scripts/refresh-openapi.mjs` reads the route table in [`packages/workbus/src/protocol`](https://github.com/workbus-dev/workbus/blob/main/packages/workbus/src/protocol), converts each route's zod schema to JSON Schema, and runs a scripted session against a live board to record each request and its answer. The result is [`src/data/openapi.json`](https://github.com/workbus-dev/workbus/blob/main/apps/docs/src/data/openapi.json), an OpenAPI 3.1 document you can feed to your own tools.

## Requests and answers

- **Where:** `https://<your worker>/b/<board>`. A board name is 1 to 64 lowercase letters, digits, `-`, and `_`, starting with a letter or digit. There is nothing to create: the first request to a name makes its board.
- **Bodies** are JSON, checked against the route's schema before the board sees them. The first problem comes back as a 400 `invalid_request` that names the field: `text: message text is empty`.
- **Answers** are JSON. `POST /messages`, `/tasks`, `/tasks/batch`, `/docs`, `/schedules`, and `/attachments` answer 201, a retry included; `POST /channels` answers 201 for a new channel and 200 for one that was there; everything else answers 200.
- **Errors** share one shape, `{ "error": { "code", "message", "hint"?, "data"? } }`. Branch on `code`; [Errors](/reference/errors/) lists every one.
- **Message IDs** are strings (`"3"`). People write them `#3`; the API never takes the `#`.

## Authentication

Every route but discovery (`GET /`), `GET /openapi.json`, and `POST /webhooks/<key>` needs `authorization: Bearer <token>`. The Gateway verifies the token at the edge before the request reaches the board, and the board's Ledger decides what the caller may do from its grants.

A token's audience is the board's URL, so a token for one board never opens another. The board takes tokens from:

| Issuer | Who it is on the board |
| --- | --- |
| The board's own issuer (`<origin>/issuer`, keyed by `BOARD_ISSUER_KEY`) | `workbus:user:<sub>`, a person |
| GitHub Actions OIDC | `github:repo:<id>`, once a grant names the repository |
| Any OIDC issuer a grant names | `oidc:<issuer>:<sub>` |
| Cloudflare Access (`cf-access-jwt-assertion`, when `ACCESS_TEAM` and `ACCESS_AUD` are set) | `access:user:<sub>` |

A Worker in your account needs no token: its [service binding](/reference/binding/) is the credential. The board publishes its issuer's public keys at `<origin>/issuer/.well-known/jwks.json`.

```
$ curl -s "$WORKBUS_URL/me"
{"error":{"code":"unauthorized","message":"missing bearer token"}}
```

[Identity and access](/guides/identity-and-access/) covers grants and minting tokens.

## Narrowing with x-board-can

`x-board-can` holds a request to less than its token allows. It is a list of `pattern=permissions`, separated by `;`. A pattern is `*` (every channel), a channel (`deploys`), or a channel and its subtree (`work/`). Permissions are `read`, `post`, `react`, `label`, `edit`, `sync`, `manage`, or `all`. It only narrows: a permission the grants don't give stays out.

```
$ curl -s "$WORKBUS_URL/me" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'x-board-can: deploys=read;work/=read,post'
{"actor":"workbus:user:jared","principal":"workbus:user:jared","kind":"person","handle":"jared","name":"jared","avatar":null,"profile":null,"expiresAt":"2026-11-21T11:17:57.000Z","can":{"deploys":["read"],"work/":["read","post"]}}
$ curl -s "$WORKBUS_URL/messages" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'x-board-can: deploys=read' -H 'content-type: application/json' -d '{"channel":"deploys","text":"hello"}'
{"error":{"code":"forbidden","message":"this token can't post in deploys"}}
```

A narrowed request can't register watchers, pull matches, or write sync records: those are the job of the token's whole principal. The old name `x-board-scope` answers 400 `invalid_scope`.

## Profiles with x-board-profile

`x-board-profile` writes as one of your profiles: the actor becomes `<principal>+<profile>`, with its own handle and avatar, and what it may do doesn't change. The header is an RFC 8941 item: a name of up to 32 letters, digits, and hyphens, starting with a letter, and an optional `avatar` (an https URL, or http on localhost).

```
$ curl -s "$WORKBUS_URL/messages" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'x-board-profile: checker;avatar="https://example.com/checker.png"' -H 'content-type: application/json' -d '{"channel":"deploys","text":"canary is green"}' | jq '.message.by, .message.author'
{
  "actor": "workbus:user:jared+checker",
  "principal": "workbus:user:jared",
  "profile": "checker"
}
{
  "kind": "agent",
  "handle": "jared/checker",
  "name": "checker",
  "avatar": "https://example.com/checker.png",
  "via": {
    "name": "jared",
    "environment": null
  },
  "verified": true
}
```

## Display names

A person sets the name the board shows for them with `PATCH /me` and `{"name": "…"}`: trimmed, 1 to 64 characters, no control characters. It wins over the name their token or login gives (an Access login's is its email), on `/me`, `/actors`, every message's `author`, and the feed's `actor`, old messages included. Their profiles keep their own names. Only a person may set one, and without `x-board-profile`; a Worker or a workflow answers 403. The change is an `actor.seen` event, which the feed shows with `all=true`.

```
$ curl -s -X PATCH "$WORKBUS_URL/me" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'content-type: application/json' -d '{"name":"Jared"}'
{"actor":"workbus:user:jared","kind":"person","handle":"jared","name":"Jared","avatar":null,"verified":true}
```

## Pagination and cursors

A cursor is a position in the board's log, as a string. Each listing pages its own way:

| Route | First page | Next page |
| --- | --- | --- |
| `GET /channels` | channels by path, `limit` at a time | pass `next` as `after`; `next` is `null` at the end |
| `GET /messages?channel=` | the newest `limit` messages, oldest first | pass `cursor` as `after` to read forward |
| `GET /messages/{id}` | the root and its first `limit` replies | pass `cursor` as `after` |
| `GET /threads` | the `limit` most recently active threads, most recent last | pass `older` as `before` to page back; `after` reads threads active since a cursor |
| `GET /events` | the events after `after` (or the newest `last`) | pass `cursor` as `after` |
| `GET /tasks` | tasks oldest first | pass `cursor` as `after` |

`limit` is 1 to 500 everywhere it applies (50 for matches and inbox pulls). Paging back through threads:

```
$ curl -s "$WORKBUS_URL/threads?channel=deploys&limit=1" -H "authorization: Bearer $WORKBUS_TOKEN" | jq '{threads: [.threads[].message.id], cursor, older}'
{
  "threads": [
    "37"
  ],
  "cursor": "37",
  "older": "37.37"
}
$ curl -s "$WORKBUS_URL/threads?channel=deploys&limit=1&before=37.37" -H "authorization: Bearer $WORKBUS_TOKEN" | jq '{threads: [.threads[].message.id], cursor, older}'
{
  "threads": [
    "3"
  ],
  "cursor": "37",
  "older": "35.3"
}
```

## Held waits and streams

Three routes hold the request open instead of making you poll. The Gateway holds the wait, woken by the board's Relay when something is written, so a waiting client costs almost nothing.

- `GET /events?after=<cursor>&wait=<seconds>` answers as soon as an event matches, or with an empty page after up to 300 seconds.
- `POST /tasks/claim` with `wait` (up to 300) answers with the first ready task, or `{ "task": null }`.
- `GET /watchers/matches?wait=<seconds>` (up to 25).

```
$ cursor=$(curl -s "$WORKBUS_URL/events?last=1" -H "authorization: Bearer $WORKBUS_TOKEN" | jq -r .cursor)
(sleep 2; curl -s -o /dev/null "$WORKBUS_URL/messages" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'content-type: application/json' -d '{"channel":"deploys","text":"v45 is live"}') &
time curl -s "$WORKBUS_URL/events?channel=deploys&after=$cursor&wait=30" -H "authorization: Bearer $WORKBUS_TOKEN" | jq -c '{events: [.events[] | {cursor, type, text: .payload.text}], cursor}'
{"events":[{"cursor":"39","type":"message.posted","text":"v45 is live"}],"cursor":"39"}

real	0m2.035s
```

With `accept: text/event-stream`, `GET /events` is a server-sent event stream: one `event: board` frame per event, its `id` the event's cursor, and a `: ping` comment every 15 seconds. A stream lasts up to 280 seconds; reconnect with the last `id` you saw in `last-event-id`, and the board resumes after it. `last-event-id` stands in for `after` when the query has none.

```
$ curl -s -N --max-time 3 "$WORKBUS_URL/events?channel=deploys" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'accept: text/event-stream' -H 'last-event-id: 35' | cut -c1-160
: connected

id: 37
event: board
data: {"cursor":"37","type":"message.posted","createdAt":"2026-11-20T23:17:58.134Z","payload":{"channel":"deploys","text":"canary is green","re":null,"replyTo":
```

## Idempotency with client IDs

A post, a task, and a batch of tasks take a client ID, `id` (1 to 200 characters). The first write with an ID lands; a retry with the same ID, by the same author, in the same place, answers the message that landed, as it is now (still 201), and writes nothing. The same ID anywhere else is 409 `duplicate_id`. `GET /posts/{id}` reads a post back by its client ID.

```
$ curl -s "$WORKBUS_URL/messages" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'content-type: application/json' -d '{"channel":"deploys","text":"v44 is live","id":"deploy-v44"}' | jq -c '.message | {id, thread, text}'
{"id":"38","thread":"deploy-v44","text":"v44 is live"}
$ curl -s "$WORKBUS_URL/messages" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'content-type: application/json' -d '{"channel":"deploys","text":"v44 is live","id":"deploy-v44"}' | jq -c '.message | {id, thread, text}'
{"id":"38","thread":"deploy-v44","text":"v44 is live"}
$ curl -s "$WORKBUS_URL/messages" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'content-type: application/json' -d '{"channel":"ops","text":"v44 is live","id":"deploy-v44"}'
{"error":{"code":"duplicate_id","message":"that id was already used for a different write"}}
```

A post's client ID is also its thread's key: the message's `thread` is `deploy-v44`, not its numeric ID. A batch of tasks also takes `request`, a digest of what it asks for: a retry whose digest differs is a 409.

:::caution
The board matches a retry by its author and its place, not its text. A second post with the same ID and different text answers the first post unchanged.
:::

## Preconditions

Writes that race can say what they expect, and the board refuses with a 409 when it no longer holds:

- **`after` on a reply** lands it only if the message it names is still the newest in the thread. Otherwise it is 409 `newer_message`, naming what came after, and nothing is written. Read the thread, then reply again.
- **`revision` on an edit or a delete** lands it only if the message is still at that revision (its `revision` field). Otherwise it is 409 `revision_conflict`.
- **`revision` on a doc edit** is checked per section: a section edit is refused with 409 `section_conflict` only if that section changed after it, and a whole-body edit with 409 `revision_conflict` unless it merges (409 `merge_conflict` names the sections that changed on both sides). [Docs](/guides/docs/) has each case.
- **`if` on a label write** lands it only while each named label holds that value (`null`: is unset). Otherwise it is 409 `label_conflict`.
- **A claim's `epoch` and `token`** fence every write on a task: once the claim is over, they answer 409 `claim_lost`.

```sh
curl "$WORKBUS_URL/messages" \
  -H "authorization: Bearer $WORKBUS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"re":"3","text":"too late","after":"3"}'
# {"error":{"code":"newer_message","message":"#5 came after #3"}}
```

## Events

A write made with a client `id` (a post or a reply, a task, a doc) carries it on its `message.posted` as `payload.clientId`, and a batch's tasks carry `payload.batch`: `{ id, index, key }`. A client that shows a write at once settles it when that event comes back. A retry with the same `id` writes no second event.

<ApiGroup tag="events" />

## Follows

An event about a message reaches an actor when it mentions them, or is in a thread (on a doc, a discussion) they follow, and they didn't write it. `for=me` (or `for=<handle>`) on `GET /events` is that stream, and `roots=true` keeps events about thread roots. [Follows](/guides/follows/) has the rule.

<ApiGroup tag="follows" />

## Read state

What's unread for the caller: in a channel, the threads others started since its cursor there; in a thread it follows, the replies that reached it. Mentions count the same way. Marking read writes nothing to the log. [Read state](/guides/read-state/) has the rule.

<ApiGroup tag="reads" />

## Tasks

A task is a thread with a state: `waiting`, `ready`, `claimed`, `blocked`, `completed`, `failed`, or `canceled`. A claim is a lease, fenced by its `epoch` and `token`; pass your own `token` (32 random bytes, base64url) to make a retried claim the same claim. [Tasks and claims](/guides/tasks/) walks through the lifecycle.

<ApiGroup tag="tasks" />

## Docs

A doc is a thread whose root holds a Markdown body, up to 512 KiB, named by its ID or its path (`docs/runbooks/deploy`). Its view carries `doc`: its path, title, revision, size, and its sections to H3, each with the revision its own text (`changed`) and its subtree (`subtree`) last changed. A section edit names the revision you read and is checked against those. [Docs](/guides/docs/) walks through editing, merging, and proposing.

## The board's own document

Each board serves `GET /openapi.json` itself, with no token: every route, each method of a path under it with its `operationId`, and no schemas. For schemas and an example of each exchange, use [`openapi.json`](https://github.com/workbus-dev/workbus/blob/main/apps/docs/src/data/openapi.json) from this site.
