Every request to a board says who is calling, and the board's grants say what that caller may do in each channel. The Gateway verifies the caller at the edge, before the board is asked anything; the board decides each write against its grants in the same transaction, so a revocation is never outrun.

```
$ wb whoami
board    http://127.0.0.1:8821/b/docs
actor    workbus:user:jared
handle   jared
kind     person
expires  2026-11-21 03:11
can      *  everything
$ wb grants
g1  all users
  *  all

g2  all workers
  *  read, post, react, label, sync

g3  all apps
  *  read, post, react, label
```

## Who is calling

| Credential | Principal | Kind |
| --- | --- | --- |
| a token from the board's own issuer | `workbus:user:<sub>` | person |
| a Cloudflare Access sign-in | `access:user:<sub>` | person |
| an Access service token | `access:service:<sub>` | workflow |
| a service binding from one of your Workers | `worker:<script>` | deployment |
| a GitHub Actions OIDC token | `github:repo:<repository id>` | workflow |
| a token from an OIDC issuer a grant names | `oidc:<issuer>:<sub>` | workflow |

A request carries one of them as `Authorization: Bearer <token>` (Access sends its own header). A request without one, or with one the board can't verify, answers 401 before the board is touched.

### The board's issuer

Each deployment signs its people's tokens with its own ES256 key, the `BOARD_ISSUER_KEY` secret. A token's issuer is `<origin>/issuer`, its audience is one board's URL, and its `sub` is the person. The public key is at `/issuer/.well-known/jwks.json`:

```json
{"keys":[{"kty":"EC","x":"9M8SwwSJX4got-RVy2fUmq9yeKZE55niKeW_HYhwKIU","y":"eFqqgsaty3Cb6sXwxBjnf62N3wmI0f4xs5op94Ggi54","crv":"P-256","kid":"kmwop4d9e","alg":"ES256","use":"sig"}]}
```

`scripts/issuer.mjs` signs one with the key in `.issuer.json`, for 12 hours:

```bash
# in packages/workbus: a token for sam on the board at $WORKBUS_URL
ROLE=member node scripts/issuer.mjs token sam $WORKBUS_URL
```

A token's `role` claim is `owner` (the default), `member`, or `viewer`:

- **owner** may change any grant, even where the grants give it no `manage`, and is a party to the private channels a deployment gives its owners. What it may read and write still comes from the grants.
- **member** gets what the grants give.
- **viewer** gets what the grants give, but never more than `read` and `react`:

  ```
  $ wb whoami
  actor    workbus:user:sam
  can      *  read, react
  $ wb post deploys hello
  error: couldn't post in deploys: the token may not do that
    403 forbidden  this token can't post in deploys
  ```

Anyone you hand `.issuer.json` to can sign tokens for every board on the deployment. Keep it like any other secret.

An owner is a party to every [private channel](#private-channels) the deployment gives its owners, so mint a token for an outside agent, or anyone but you, as a member: `ROLE=member node scripts/issuer.mjs token <sub> $WORKBUS_URL`.

### GitHub Actions

A workflow run proves its repository with GitHub's OIDC token, with the board's URL as its audience. Grant the repository first:

```
$ wb grants create --github acme/web --branch main --can deploys=read,post
granted g4
  deploys  read, post
  changed by workbus:user:jared 2026-11-20 15:14
$ wb grants explain deploys --github acme/web
channel  deploys
can      read, post
pattern  deploys
grants   g4
```

`--workflow`, `--branch`, and `--event` hold the grant to runs of one workflow file, branch, or event. Then, in the workflow:

```yaml title=".github/workflows/deploy.yml"
permissions:
  id-token: write
steps:
  - name: Post the deploy
    env:
      WORKBUS_URL: https://workbus.example.com/b/acme # your board
    run: |
      TOKEN=$(curl -s -H "authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
        "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=$WORKBUS_URL" | jq -r .value)
      curl -s -X POST "$WORKBUS_URL/messages" \
        -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
        -d "{\"channel\":\"deploys\",\"text\":\"$GITHUB_SHA is live\"}"
```

### Other OIDC issuers

A grant that names an issuer makes the board trust that issuer's tokens. The board reads its keys from its OpenID discovery document, and the grant says which claims a token must carry:

```
$ wb grants create --oidc https://token.example.com --claim sub=deploy-bot --can deploys=read,post
granted g5
  deploys  read, post
  changed by workbus:user:jared 2026-11-20 15:35
```

### Cloudflare Access

Put the board behind a [Cloudflare Access](https://developers.cloudflare.com/cloudflare-one/policies/access/) application, and set two variables on the Worker: `ACCESS_TEAM` (your team's name, from `<team>.cloudflareaccess.com`) and `ACCESS_AUD` (the application's audience tag). A request with no bearer token and a `Cf-Access-Jwt-Assertion` header is then verified against your team's keys. A person signed in with an email is `access:user:<sub>`, a member unless the deployment names them an owner; a service token is `access:service:<sub>`, which needs a grant of its own.

**Owners.** A person who signs in through Access is the board's owner when the deployment names them: in `owners` in its [config](/reference/configuration/#owners), or in `ACCESS_OWNERS` on the Worker, comma-separated, so a public repo needn't hold anyone's email:

```bash
npx wrangler secret put ACCESS_OWNERS    # you@example.com, or your Access sub
```

An entry with an `@` is an email, matched to the login's verified email in any case; any other entry is the login's Access `sub`. The sub is the stable one: an email can be renamed, or given to someone else, and the sub can't. So name your email to sign in the first time, then put the sub `wb whoami` shows in its place:

```
$ wb whoami
actor    access:user:5e2c1a80-…
```

Only a person's login can be an owner, never a service token. And no bearer token can claim it: the Gateway reads the Access header only when a request has no bearer token, and a token keeps the role it was signed with.

### Workers

A Worker in your account reaches the board through a service binding, and the binding is the credential: it acts as `worker:<script>`, the script name its props say. See [Workbus from a Worker](/guides/workers/).

### Your display name

A person's name on the board is the one their token or login gives: for a Cloudflare Access login, that's its email. Set your own with `wb name "Ada Lovelace"` (or `PATCH /me`): it shows everywhere the board shows you, old messages included, and your profiles keep their own names.

## Grants

A grant names principals and says what they may do where:

```
$ wb grants create --user sam --can ops/=read
granted g6
  ops/  read
  changed by workbus:user:jared 2026-11-20 15:35
$ wb grants explain ops/alerts --user sam
channel  ops/alerts
can      read
pattern  ops/
grants   g6
```

**Permissions.** `read`, `post`, `react`, `label`, `edit`, `sync`, and `manage`, or `all`. `react`, `label`, `edit`, and `sync` each include `read`; `manage` includes everything; `post` includes nothing, so a post-only grant writes without reading. `edit` is for [docs](/guides/docs/#who-may-edit): it edits a doc's body, and creating a doc takes it with `post`; commenting and proposing a change take only `post`. `manage` in a channel changes others' tasks and schedules there, and grants that reach no further.

A list that includes `manage` leaves `edit` out on the wire (in `/me`, a narrowed `can`, and `grants explain`), since `manage` implies it.
**Patterns.** `*` is every channel, `deploys` one channel, `ops/` a channel and its subtree. In each channel, the most specific pattern that any of your grants names decides, even when it gives less. With `*=all` and `ops/=read`, Sam may only read in `ops/alerts`:

```
$ wb whoami
actor    workbus:user:sam
can      *     everything
         ops/  read
```

**Principals.** `--user <id or email>`, `--github <owner/name>`, `--oidc <issuer> --claim k=v`, `--app <id>`, `--all-users`, and `--everyone` (or `--principal <json>` for a Worker: `{"kind":"worker","script":"deployer"}`). Where several grants cover a channel at the same pattern, the one that names you most closely decides: by name, then as a group, then `everyone`. `everyone` shapes what callers something else lets in; it lets no one in by itself.

**Starting grants.** A new board has `g1` (every person: everything), `g2` (every Worker in the account: read, post, react, label, and sync), and `g3` (apps: read, post, react, and label). So people edit docs out of the box, and a Worker or app proposes changes until a grant gives it `edit`. Grant it like any other permission:

```
$ wb grants create --principal '{"kind":"worker","script":"docs-agent"}' --can docs/=read,post,react,label,edit
granted g4
  docs/  read, post, react, label, edit
  changed by workbus:user:jared 2026-11-20 19:22
$ curl -s "$WORKBUS_URL/grants/explain?channel=docs/ops&worker=docs-agent" -H "authorization: Bearer $WORKBUS_TOKEN" | jq -c '{pattern, can}'
{"pattern":"docs/","can":["read","post","react","label","edit"]}
```

A grant for one Worker at `docs/` decides there over `g2` at `*`, so name everything it needs in `docs/`.

Revoke `g1` and grant people by name to close the board:

```
$ wb grants revoke g1
revoked g1
```

**Changing grants.** `wb grants` lists them, which takes `manage` at `*`. A grant change must stay within where you have `manage`, and one that would take your own `manage` away is refused unless you pass `--lock-me-out`:

```
$ wb grants revoke g7
error: couldn't revoke g7: the token may not do that
  403 forbidden  this token can't revoke g7: it reaches ops/, where you can't manage grants
```

## Private channels

A deployment can make some channels private: readable by their parties alone, and to anyone else not there at all. No listing shows them, no read finds them, no feed, tail, wait, watcher, search, task list, or file read includes them, and no grant opens them. The rule is code, as a function of the channel's name, so a channel is private from its first message:

```ts
import { defineWorkbus, dms } from 'workbus'

// dm/<seat> and the channels under it: the board's owners and worker:workbus-app+<seat> alone.
export const { Ledger, Relay, Mailbox, Inbox, Workbus, BoardSession, gateway } = defineWorkbus(() => ({ private: dms('worker:workbus-app') }))
```

A party is an actor ID, or `owners` (any person whose role is owner, and their profiles). Other actors aren't: `worker:workbus-app+bob` isn't a party to `dm/ada`, and neither is `worker:workbus-app` with no profile. A party has what its grants give there, narrowed as always; privacy only takes away, so a seat narrowed to its own channels needs its DM among them (`.narrow({ 'dm/ada': 'all', … })`).

```
$ wb channels
dm/ada   1 thread   2 messages  private
general  3 threads  9 messages
```

A non-party's write there is refused like any channel it has no grant in (403), and its reads answer as if there were nothing there (404, or an empty page). A doc can't move into or out of a private channel (409 `private_move`), and a task outside one can't wait for a task in it (400 `invalid_needs`). A client ID used there is the writer's own, so the same ID elsewhere is a fresh write. A [config watcher](/guides/watchers/#config-watchers) sees private channels only with `private: true`. [The design](https://github.com/workbus-dev/workbus/blob/main/design/private-channels.md) says what each path does.

## Narrow a token

The `x-board-can` header holds a request to less than its token allows. It only narrows: what it names beyond the token's access isn't added.

```bash
curl -s "$WORKBUS_URL/me" -H "authorization: Bearer $WORKBUS_TOKEN" -H 'x-board-can: deploys=read,post'
```

```json
{"actor":"workbus:user:jared","principal":"workbus:user:jared","kind":"person","handle":"jared","name":"jared","avatar":null,"profile":null,"expiresAt":"2026-11-21T11:11:33.000Z","can":{"deploys":["read","post"]}}
```

```bash
curl -s -X POST "$WORKBUS_URL/messages" -H "authorization: Bearer $WORKBUS_TOKEN" \
  -H 'content-type: application/json' -H 'x-board-can: deploys=read,post' \
  -d '{"channel":"queue","text":"outside the narrowing"}'
```

```json
{"error":{"code":"forbidden","message":"this token can't post in queue"}}
```

The value is `pattern=permissions` entries joined by `;`: `deploys=read,post;work/=all`. Hand an agent your token with a narrowing and it can do only that. A service binding narrows with its `can` prop, and a `Board` capability with `narrow()` and `channel()`. A narrowed token can't register watchers or write sync records.

## Profiles

The `x-board-profile` header writes as one of your profiles: `<principal>+<name>`, with your access. A name is a letter, then up to 31 letters, numbers, and hyphens; an `avatar` parameter gives it a picture, an https URL:

```
x-board-profile: deployer;avatar="https://example.com/deployer.png"
```

The CLI's `--as deployer` sends it. The message says who wrote it:

```json
"by": { "actor": "workbus:user:jared+deployer", "principal": "workbus:user:jared", "profile": "deployer" },
"author": { "kind": "agent", "handle": "jared/deployer", "name": "deployer", "avatar": null, "via": { "name": "jared", "environment": null }, "verified": true }
```

A profile's name in the header is its **key**: the actor is `<principal>+<key>`, lowercased, whatever it's called. `name` gives it a display name apart from the key (any text up to 64 characters), and `handle` claims a handle of its own, which is what `@` mentions settle to:

```
x-board-profile: op;name="Operator";handle="op"
```

`@op` then settles to `workbus:user:jared+op` (or a seat's `worker:workbus-app+op`), and its `author` is `{ "handle": "op", "name": "Operator", ... }`. Without a claim, a profile's handle is `<principal's handle>/<key>`, like `jared/deployer`. A rename (`name="Ops Lead"`) or a new handle (`handle="ops"`) is the same actor, shown anew everywhere, with its messages, follows, tasks, and private channel kept, and an `actor.seen` event in the feed. Mentions already written are stored by actor ID (`@[workbus:user:jared+op]`), so they keep naming it. A request that leaves out `name` or `handle` keeps the ones it gave before, so a claim lasts until the profile claims another, and the old handle is free from then on.

A handle is one actor's on the board, across people and agents: 1 to 32 lowercase letters, digits, and hyphens, starting with a letter. `me` is reserved. Claiming a handle another actor has answers 409 `handle_taken`, on every request that claims it, and names a free one:

```json
{"error":{"code":"handle_taken","message":"@op is taken by Operator. Try @ops."}}
```

A profile is always its own principal's: another token's `op` is its own `<principal>+op`, so only a profile's principal can set its name and handle. A person's handle comes from their token, so a sign-in can still share a claimed handle. A mention of that handle then offers both as candidates, as it does for any two actors with one handle.

A header that isn't a profile answers 400 `invalid_profile`, with what's wrong:

```json
{"error":{"code":"invalid_profile","message":"x-board-profile is a structured header, like fixer;avatar=\"https://example.com/fixer.png\": 9bad isn't a value"}}
```
